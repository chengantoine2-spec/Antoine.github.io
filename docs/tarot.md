# 塔罗牌窗口：实现说明

> 窗口 id `tarot`、路由 `/tarot`。做的是"抽牌 + 逐张翻开 + 出解读"。
> 这一篇记的是**数据从哪来、素材怎么进来的、牌阵坐标怎么读、有哪些坑**。

## 一、这是什么，不是什么

- **是**：78 张牌的牌义数据 + 一套牌面图 + 三个牌阵的排布 + 洗牌/抽牌/翻牌/解读的完整流程。
- **不是**：讲解塔罗知识的百科（那是饥荒 Wiki 窗口那种形态），也不是在线服务 ——
  **没有网络请求**，全部数据都在仓库里，占卜记录只在浏览器本地。

## 三、素材：映射是怎么定下来的（这一节最值得看）

### 问题

上游 `AkaxiTarot/` 里是 `0.png` ~ `77.png`，**没有任何"第 N 张是哪张牌"的说明**。
来源清单 `Script/akaxi-tarot.txt` 里每行的文件编号是**乱的**：

```
第 1~32 行   → 文件名后缀 _01 … _32       （连号）
第 33 行     → _63                        ← 跳到 63
第 34~36 行  → _64 _65 _66
第 37 行     → _33                        ← 又跳回 33
...
```

### ⚠️ 这里踩了一个大坑（2026-10-06）

我先假设「`_NN` 后缀就是标准牌序」：`_01`~`_22` 大阿卡纳、`_23`~`_36` 权杖、
`_37`~`_50` 圣杯、`_51`~`_64` 宝剑、`_65`~`_78` 星币，然后按 `文件号 → _NN → 牌` 生成了素材。

**这个假设是错的。** 我当时抽查了 `0 / 21 / 22 / 29` 四张，全对 ——
但那四张**恰好落在"两种假设结果相同"的区间里**（第 32 号文件之前，`_NN` 与位置顺序一致）。
等真去比对 32 号之后的文件，才发现全错：

| 文件 | 错误假设的结论 | 实际牌面 |
|---|---|---|
| `32.png` | 宝剑王后 | **KING of WANDS** |
| `34.png` | 星币一 | **KNIGHT of WANDS** |
| `36.png` | 权杖侍卫 | **ACE of CUPS** |
| `60.png` | 星币七 | **KING of SWORDS** |
| `77.png` | 星币国王 | **PAGE of COINS** |

**两条教训：**

1. **抽样点必须落在"两个假设结果不同"的区间。** 先验的四张全在重合区，等于没验。
2. **映射对不对只能靠肉眼比对牌面上印的牌名** —— 文件在、能解码、比例对，
   这些全都测不出"图配错了牌"。`verify-tarot.mjs` 抓不到这类错
   （它验的是存在性 / 可解码 / 比例），**别再以为跑过它就安全了**。
   错配 46 张的那一版，33 项校验全绿。

### 正确的规则

**`AkaxiTarot/` 的文件顺序（0~77）就是牌的顺序**，而且
**宫廷牌是 国王 → 王后 → 骑士 → 侍卫**（不是常见的 侍卫 → 骑士 → 王后 → 国王）：

```
 0 ~ 21    大阿卡纳：愚者 → 世界
22 ~ 35    权杖：Ace 一 ~ 十，接着 国王、王后、骑士、侍卫
36 ~ 49    圣杯：同上
50 ~ 63    宝剑：同上
64 ~ 77    星币（Coins / Pents）：同上
```

⚠️ **`_NN` 后缀不是牌序**，它只是上游媒体站的编号（按帖子分批，所以会跳）。
真正能用的信号是**文件顺序本身**。

这条规则已**逐个肉眼验过 13 张**，覆盖每个花色与每个边界：
`0 / 21 / 22 / 29 / 32 / 34 / 36 / 46 / 50 / 60 / 64 / 74 / 77` —— 全部吻合。
站主给的命名清单（`00-the-fool` … `coins-page`）与这条规则**完全一致**，
两个独立来源互相印证。

**这条规则已经落进代码**：`tools/tarot-assets.py`（`npm run tarot:assets`）按文件名推出牌 id，
所以以后换图不用再手工"翻译"一次 —— 见第九节。

### 成品

- 源目录 `tarot/tarot-lab/AkaxiTarot/` 已按站主的命名方案重命名完毕（78 个文件，
  `00-the-fool.png` … `coins-page.png`），本身就是一份自解释的素材库。
- 应用用的素材在 `public/tarot/cards/<牌 id>.webp`，**牌 id 沿用上游 `cards.json` 的
  `link` 字段名**（`Fool` / `Wands01` / `Pents14`）——
  这样"哪张牌配哪张图"不需要第二份映射表，`link` 换个后缀就是图片地址。

### 体积

原始 PNG 78 张 = **31.6 MB**（约 420 KB/张），直接进仓库、原样发给浏览器都不现实。
转成 WebP（q82、尺寸不变）之后：

| | 总量 | 平均 |
|---|---|---|
| 原始 PNG | 31.6 MB | ~420 KB |
| **WebP q82（在用）** | **约 4 MB** | **~53 KB** |

省了约 **11 倍**。质量档位实测过：q75 ≈ 2.9 MB、q82 ≈ 4 MB、q90 ≈ 5.5 MB。
牌在界面上最大也就显示到 ~152px 宽（源图 350px），q82 看不出差别。

牌图按需加载（`<img loading="lazy">`），一次占卜最多同时要 10 张 ≈ 500 KB。

> 78 张的尺寸**统一是 350×600**。（曾经有一张例外：星币十的源图只有 224×384，
> 站主 2026-10-06 补了一张正尺寸的，现在全齐了。）

## 五、牌阵坐标怎么读

坐标**不是** 0~1 的相对百分比，单位是「**牌高**」：

```ts
positions: [{ label: '过去', hint: '…', u: -0.883, v: 0 }, …]
```

- `u/v` 是**牌心**位置，`v = 1` 就是往下挪一张牌的高度；横向用同一个单位。
- 牌宽固定是 `CARD_RATIO`（350/600 ≈ 0.583）个牌高，不用另外写。
- **画布多大、牌多大是算出来的**，牌阵定义里**没有**宽高比、也没有像素：

```
包围盒 = 所有牌心的最小外接矩形（旋转的牌按转完之后的占位算）
scale  = min(可用宽 / 包围盒宽, 可用高 / 包围盒高)     ← 每「牌高」多少 px
```

`lib/tarot/layout.ts` 的 `layoutSpread()` 干这件事，组件只把算出来的数贴到 style 上。
好处：**牌永远是"塞得进又能多大就多大"**，换窗口尺寸、加牌阵都不用调数值。

> **为什么改成这样（踩过的坑）**：第一版我给每个牌阵手写了一个画布宽高比，
> 凯尔特十字写的是 **1.55（横的）**。可这个牌阵**天生是竖的** ——
> 右边那一列是 4 张牌叠起来，整体高 ≈ 4.3 个牌高、宽 ≈ 3 个牌高。
> 结果是纵向白空着、画布被宽度卡住，**牌只有 51px 宽**，牌面完全看不清。
> 改成按内容算之后是 **74px**（+45%）。**别再手写画布比例。**

⚠️ 几个不能忘的点：

- 位置给的是**牌心**，`.tarot-slot` 里有一句 `transform: translate(-50%, -50%)`。
  删了它整个牌阵会朝右下偏半张牌。
- 牌宽写进 CSS 变量 `--card-w`，序号角标字号、圆角、内边距全部 `calc(var(--card-w) * …)`
  → 牌阵整体等比缩放，没有第二套断点数值。
- 间距都是"牌边到牌边留多少"，注释里写了具体数。改一个要重验会不会压住邻居。
- **旋转的牌要把它转完之后的占位算进包围盒**（凯尔特十字第 2 张是横放的），
  否则包围盒会算小、牌被裁掉一截。`halfExtents()` 负责这件事。
- 那张横放的牌，**序号角标要反向转回来**（`TarotCardFace` 收到 `rotate` 后给角标加 `-rotate`），
  不然数字跟着牌一起躺倒。

## 六、抽牌逻辑

`lib/tarot/draw.ts`：

- **种子进结果**：同一个 `seed` 一定抽出同一副牌、同一套正逆位。
  种子用 `crypto.getRandomValues` 取，**不用 `Math.random`**（同一毫秒内可能撞出相同序列）。
  PRNG 是 mulberry32。
- **正逆位从同一条随机流里取**（50%），不另开随机源 —— 否则复现时两边对不上。
- **抽出的牌不重复**：洗整副牌再取前 N 张。
- ⚠️ 洗牌前**必须拷贝**（`shuffle([...CARDS], rng)`）：`CARDS` 是模块级常量，
  就地洗会污染全局，下一次抽牌就没有随机性了。

### 回顾历史为什么不用 seed 重算

`fromStored()` **用存下来的牌 id 重建**，不用 seed 重算。
seed 重算依赖洗牌算法一字不变，哪天换了算法，用户翻旧记录会看到**另一副牌** —— 那比"看不到"更糟。
seed 仍然存着，它的价值是"能精确复现当时的随机"，不是拿来显示历史的。
任何一张牌在牌表里找不到（牌组换过）就整条记录不展示，**不显示位置错乱的半条解读**。

## 七、界面上的几个决定

- **翻开状态是逐张的**（`revealed: boolean[]`），不是"翻开了几张"：
  点第 5 张就只翻第 5 张。「全部翻开」按顺序每 260ms 翻一张，让每张牌都被看到。
- **没翻开的牌不给解读**：解读栏只渲染翻开了的那几条；
  **整体构成**（统计那几句）要全部翻完才出现 —— 它讲的是整副牌的构成，
  早显示等于剧透，而且那份统计本身也会跟着翻牌变。
- **逆位 = 让图片自己转 180°**（`.tarot-card__art--reversed`），不是把整张牌翻过来 ——
  位置与序号角标不能跟着倒。
- **序号角标画在翻转层外面**：翻牌时它不该跟着转。牌阵位置 ↔ 解读条目靠这个号对上。
- **牌背是自绘 SVG**（`CardBack.tsx`）：上游五套牌图里**一张牌背都没有**
  （全库按 `back|reverse|cover` 搜过，零命中；`AkaxiTarot` 正好 78 张 = 78 张牌）。
  面朝下的牌全程都在屏幕上，用位图就得准备浅深两张；SVG 走主题令牌，两套主题自动跟着变。
  图案是一只眼 —— 照牌名「阿卡西之眼」来的。
- **图片挂了要有兜底**：按站里的规矩"宁可写待接入，也不要给一个裂图"，
  加载失败退回一张写着牌名的底板（`.tarot-card__fallback`），不显示浏览器的裂图图标。
- 版式：`container-type: inline-size` 跟着**窗口宽度**走，`≥780px` 才把解读栏摆到右边；
  窄窗上下各占一半、两边各自滚，都比"挤成一条"好。

| 键 | 内容 |
|---|---|

## 九、换图 / 补图：一条命令

**日常只需要记住这一条** —— 把图按命名方案丢进源目录，然后：

```bash
npm run tarot:assets            # 有变化才写
npm run tarot:assets -- --check # 只看会改什么，不写盘
```

它做的事：读 `tarot/tarot-lab/AkaxiTarot/` → **按文件名推出牌 id** →
转 WebP 写进 `public/tarot/cards/<牌 id>.webp` → 报告 `新增 / 更新 / 未变`。

名字的对应关系（就是这一条命令替你翻译的东西）：

```
coins-10.png        ->  Pents10.webp         （星币十）
wands-king.png      ->  Wands14.webp         （权杖国王；宫廷牌 king=14 queen=13 knight=12 page=11）
cups-01-ace.png     ->  Cups01.webp
00-the-fool.png     ->  Fool.webp
10-wheel-of-fortune.png -> Wheel_of_Fortune.webp
```

它是**幂等**的：比的不是时间戳，而是**重新编码之后的字节**。
所以源图重新存一遍（像素没变）也会报「未变」，不会白写一堆文件。
改法只有一处：`tools/tarot-assets.py` 顶部的 `SUIT_OF_PREFIX` / `RANK_OF_TAIL`。

**它会拦住这些情况**（退出码 1，不会悄悄放过去）：

- 文件名不符合命名方案（比如丢进来一个 `screenshot.png`）
- 文件名和牌对不上（把 `07-the-chariot.png` 改成 `07-the-fool.png` —— 会告诉你第 07 张大阿卡纳是 `Chariot`）
- 牌表里有牌在源目录里找不到图（少一张）
- **比例不是 350:600**（牌阵布局是按它算的，比例不对会被裁掉一块）

⚠️ 但它**验不出"图配错了牌"** —— 它能保证"哪个文件该叫什么"，
没法知道那张图画的到底是哪张牌（2026-10-06 就是这么错了 46 张）。
所以命令会把每一张的对应关系打印出来，**换过图之后扫一眼那一列**，必要时拼张联系表对着牌面看。

### 从零重新拿一份源素材

源目录 **43 MB，不进构建**（`public/tarot/cards/` 那 4 MB 才是产物）。
如果它不在了：

1. 拉上游 `AkaxiTarot/*.png`。⚠️ **`raw.githubusercontent.com` 时快时慢**
   （实测同一时段从 3 KB/s 到 38 KB/s 都有）。慢的时候别用 Python 单线程 urllib，用 `curl --parallel`：
   ```
   # 配置文件里 output 的路径要用**正斜杠**：反斜杠在 curl 配置里是转义字符，
   # 写成 C:\Users\... 会被吃成乱码路径、文件落到奇怪的地方（踩过，静默失败 0 个文件）
   url = "https://raw.githubusercontent.com/look-fate/tarot-lab/main/AkaxiTarot/40.png"
   output = "C:/temp/akaxi/40.png"
   ```
   然后 `curl -K cfg --parallel --parallel-max 6 --retry 6 --retry-all-errors`。
2. **按第三节的规则改名**（文件顺序 = 牌顺序，宫廷牌是 国王→王后→骑士→侍卫）。
   ⚠️ **别用 `_NN` 后缀推牌序**。
3. 跑到 `npm run tarot:assets` 报 `新增 78` 为止，然后在应用里再肉眼扫一遍（第三节的两条教训）。

换成别的牌组时，只要文件名还是牌 id（`Fool` / `Wands01` / `Pents14`），
**数据层与组件一行都不用改**。

> ⚠️ **这个脚本是 Python 而不是 .mjs**（`tools/` 里其余都是 Node）：
> Node 内置模块**编不出 WebP**，而项目规矩是"不引依赖"（`sharp` 那种重家伙免谈）。
> 它只在**改素材时**用一次，不进构建、不进产物。
> 要求：`python` 在 PATH 上 + Pillow（`python -c "import PIL"` 能过就行）。
